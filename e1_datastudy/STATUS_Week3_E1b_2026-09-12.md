# Paper H — E1b renamed-schema control — status (12 Sep 2026)

Purpose: test the memorisation threat recorded in STATUS_Week2. Same five schemas, every table and
column renamed to a synonym (202 identifiers; `rename_maps/*.json`), dataset names and documentation
references removed from the business cases, synonyms applied to the prose (`cases/*_r.txt`, MD5s in
`cases_MD5.txt`). Types, constraints, CHECK lists, row targets, prompts, seeds unchanged. Validation
before the run: renamed DDLs load in PostgreSQL; SynthData `auto` 100 % on all five; the human
fixtures reload into the renamed DDLs at 100 % (chinook, northwind, dellstore2, pagila; employees cache
capped so not checked). Generated by `rename_schema.py`; E1 originals untouched (MD5s verified).

Run: `RUN_E1B_RENAMED.cmd` on Vijay's PC, 12 Sep 09:07–11:09 local, 20 cells = {plan, direct} ×
{Claude Sonnet 4.6, GPT-4o} × 5 renamed schemas × 1 run. Scored from `arms_snapshot.zip`
(12 Sep 11:12) into `scores/pc_r/`, `metrics/pc_r/`; comparison table `results/E1b_renamed_vs_original.csv`
(paired with the E1 run-1 cell of the same schema × provider × arm).

## Result 1 — validity is unaffected by renaming (direct arm)
Direct-emission load rate, original vs renamed (10 paired cells): median 0.992 vs 0.982, mean 0.962 vs
0.971, Wilcoxon p = 1.0. Per cell: chinook 93.8→99.2 / 99.7→99.7; northwind 98.4→97.2 / 77.3→87.8;
dellstore2 100→97.7 / 100→100; pagila 99.9→99.6 / 94.7→96.1; employees 99.8→95.4 / 98.6→98.7
(Claude / GPT-4o). The models' constraint-satisfying ability does not depend on knowing the dataset.

## Result 2 — the direct arm's fidelity advantage was memorisation
Categorical JS distance to the human data, direct arm, original → renamed: median 0.245 → 0.732
(Wilcoxon p = 0.016); value coverage 0.94 → 0.51 (p = 0.062); numeric/date KS 0.522 → 0.602 (p = 0.023).
Claude, which reproduced the published data exactly in E1, loses it under renaming: JS chinook
0.000→0.326, northwind 0.000→0.263, pagila 0.000→1.000 (value coverage 1.0→0.0), employees 0.054→0.085;
dellstore2 (never memorised) 0.406→0.589. GPT-4o, which was already at JS ≈ 1.0 on chinook/pagila,
changes little (northwind 0.587→1.0, employees 0.083→0.389). Under renamed schemas the direct arm's
categorical fidelity (median JS 0.73) is closer to the plan arm's (median 1.0) than the E1 gap
(0.08 vs 1.0) suggested — the E1 RQ3 headline must be reported as a memorisation effect, with the
renamed condition as the honest estimate of fidelity on an unseen schema.

Residual cue: Claude's renamed-Pagila plan still generated loan dates in 2005–2006 (the Sakila era),
so structural memorisation survives identifier renaming to some degree; this stays a threat.

## Result 3 — plan arm under renaming: same engine defects, more often
Plan-arm load, original → renamed: chinook 100→100 / 100→100; northwind 100→**27.4** / abort→abort;
dellstore2 93.8→100 / 93.9→93.7; pagila 100→**89.7** / 100→100; employees 100→100 / 100→**abort**.
Every sub-100 renamed cell is again SynthData defect #6 (`expr` gets dates as strings:
`row.purchase_date + 14` → "2023-05-3014", 500 type errors + 500 FK cascade on northwind × Claude;
`row.loan_date + …*86400000` on pagila × Claude; `row.start_date.getFullYear` abort on employees ×
GPT-4o; `row.purchase_date.getTime` abort on northwind × GPT-4o) or #7 (`fk` on PK, dellstore2 ×
GPT-4o, 178 duplicates). New, #8: a self-referencing `{gen: fk, ref: items.item_id}` on a NOT NULL
column emits NULL for the first rows (12 NOT NULL rejections, dellstore2 × GPT-4o). With the
synonym names the LLMs reached for `expr` date arithmetic in 4 of 10 plans versus 2 of 20 in E1.
Plan mean load 0.888 (E1 run 1) → 0.711 (renamed). This is the strongest evidence in the study that
the plan arm's validity ceiling is set by the engine's handling of LLM-written plans, not by the LLM.
